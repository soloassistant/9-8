## 1. 缺陷 A —— 输入框宽度 0（"打不了字"）

### 现象
375×812 下量到的真实 `<input class="weui-input">` 的盒子是 **0 × 20.6**（宽 0）。它的宿主
`taro-input-core.index-module__textInput___nTQKd` 只有 32px 宽。截图里能看到那是一个**近乎正方的灰色小胶囊**，
placeholder「输入指令，如「把评审会挪到明天」」**一个字都不显示**。

### 证据（线上实测）
```
input.weui-input                          rect = 0 × 20.6      width = 0px
taro-input-core.index-module__textInput   rect = 32 × 40      padding = 15.9999px / 15.9999px
输入行子元素（375 宽，行宽 327）：
  [0] modeButton   taro-button-core   36px   flex 0 0 auto
  [1] textInput    taro-input-core    32px   flex 1 1 0%     ← 只剩 32px
  [2] VoiceButton  taro-view-core    173px   flex 0 1 auto   ← 元凶：占了 173px
  [3] sendButton   taro-button-core   62px   flex 0 0 auto
```

### 根因
`src/components/VoiceButton/index.module.scss` 的 `.wrapper { width: 100% }`。它既是按钮的外层容器
（晨报输入栏里的直接 flex 子项），`width:100%` 让它以**整行宽**作为 flex basis；行内其余三项都是
`flex: 0 0 auto` 不可压缩，只有它能收缩，于是它吃掉绝大部分空间，把 `flex:1` 的输入框压到 32px。
32px 又恰好等于 `.textInput` 的左右 padding 之和（`$spacing-lg` = 32rpx = 16px × 2），内容盒被压成 **0**，
内部那个 `width:100%` 的 `<input>` 于是也成了 0px。

### 修法
```scss
/* 紧凑态（仅晨报页输入栏在用） */
.wrapper.compact { width: auto; flex: 0 0 auto; }
```
- 影响面已核对：`<VoiceButton>` 全仓只有两个调用点 —— `pages/briefing/index.tsx:1272`（`compact`）与
  `pages/learnDetail/SpeakingDrill.tsx:138`（非 compact，仍需 `width:100%`），所以只加 `.wrapper.compact` 不会误伤。
- 按钮本身的定宽由 `.compact.button { width:72rpx; min-width:72rpx }` 决定（特异性与 `.wrapper.compact` 相同但
  写在后面，且作用于 button 自身），不受影响 —— 构建产物里两条规则都在。

### 验证
`taro-input-core` 由 32px → **169px**，内层 `<input>` 由 0 → **137px**（= 169 − 32 padding，完全吻合）。
截图里 placeholder 正常显示。

## 2. 缺陷 B —— 输入栏被底部 TabBar 压住 17px

### 现象 / 证据
底部 TabBar（`.taro-tabbar__tabbar`）实测**固定 50px**（375 / 390 / 1280 三档都是 50）。
输入栏 `bottom` 只有 33px ⇒ 其底部 17px 落在 TabBar 区域内：

| 视口 | 输入栏 bottom | TabBar top | 重叠 |
|---|---|---|---|
| 375×812 | 779 | 762 | **17.0px** |
| 390×844 | 809.7 | 794 | **15.7px** |
| 1280×800 | 756 | 750 | **6.0px** |

### 根因
源码 `src/pages/briefing/index.module.scss`：
```scss
.h5Fix { bottom: calc(66px + env(safe-area-inset-bottom)); }
```
作者意图是"避让 50px TabBar 再上移 16px = 66 真实 px"。但**在 Taro H5 里小写 `px` 被当作设计 px（750 基准）**，
构建产物是：
```css
.index-module__h5Fix___Y5d0U{bottom:calc(1.76rem + env(safe-area-inset-bottom))}
```
`1.76rem` 在 375 视口（根字号 18.75px）只有 **33px**。而 390 / 1280 档的 `bottom` 分别是 34.32 / 44px ——
全都随视口缩放，正是"被当作设计 px"的指纹（真 66px 应当三档恒为 66）。

### 修法
```scss
.h5Fix { bottom: calc(66PX + env(safe-area-inset-bottom)); }
```
大写 `PX` 逃过 Taro pxtransform（CSS 单位大小写不敏感，大写只是给构建器看的）。
构建产物核对：`.h5Fix{...bottom:calc(66PX + …)}` 原样保留。
> 这与 `src/app.scss` 里早已在用的 `500PX`（`html { font-size: calc(min(100vw, 500PX) / 20) }`）是同一个手法 —— 本项目此前已踩过一次，这次是同一坑的另一处。

### 验证
三档视口 `bottom` 全部变为 **66px**，与 TabBar 重叠全部为 **0px**。

## 3. 缺陷 C —— AI 悬浮球渲染在屏幕顶部

### 现象 / 证据
线上 375×812 实测：
```
#ai-fab 的父 wrapper  rect = { x:0, y:0, w:375, h:118 }   ← 贴在视口顶端
内联 style attr          = "bottom: calc(50px + env(safe-area-inset-bottom) + 340rpx)"
getComputedStyle().bottom = 694px     ← 恰等于 812 − 118 = 视口高 − 自身高
```
`694px` 就是"`bottom: auto` 时元素落在静态位置"的典型读数。截图佐证：🤖 橙色球和它的提示气泡
（「帮我梳理一下今天的时间安排」）都渲染在**页头**，气泡盖住了问候语那一行。

### 根因
`src/components/AiAssistant/index.tsx` 原写法：
```ts
const fabStyle = { bottom: `calc(${isH5 ? '50px' : '0px'} + env(safe-area-inset-bottom) + ${100 + offset}rpx)` };
```
React 把这段字符串原样写进 `style` 属性。**`rpx` 不是浏览器认得的 CSS 单位**，于是整条 `calc()` 在解析期
就被判非法并**整条丢弃**（不是"留个错值"）—— `bottom` 退回 `auto`，元素落到静态位置。
浏览器内直接验过：`CSS.supports('bottom','calc(50px + 0px + 340rpx)') === false`，
而 `CSS.supports('bottom','calc(50px + 0px + 9.0667rem)') === true`。

> 注意：小程序端（WXSS）`rpx` 是**原生合法**单位，所以这处只在 H5 坏 —— 也正因如此，它此前没被发现。

### 修法
H5 分支自己把设计 px 换算成 rem；小程序分支保持 `rpx` 原样：
```ts
const FAB_BASE_OFFSET_RPX = 100;
const DESIGN_PX_PER_REM = 750 / 20;   // 依据 app.scss 的根字号公式：750 设计宽 = 20rem ⇒ 1 设计 px = 1/37.5 rem
// H5：`calc(50px + env(safe-area-inset-bottom) + ${((100 + offset) / 37.5).toFixed(5)}rem)`
// weapp：`calc(0px + env(safe-area-inset-bottom) + ${100 + offset}rpx)`
```
- `1 设计 px = 1/37.5 rem` 不是猜的：构建产物里 `$spacing-md: 24rpx → 0.64rem`、`66px → 1.76rem`，
  两处都精确等于 `n / 37.5`。
- ⚠️ **不要用 `Taro.pxTransform` 顶替**：它按 **1/20 rem** 换算（面向"设计 px ≠ rpx"的项目），在本项目会放大一倍；
  且它假设根字号 = `100vw/20`，而本项目根字号**封顶在 500px**，>500px 视口会一起错。
- weapp 分支在 H5 构建里被完全消除（构建产物中该模板只剩 H5 那一处，`rpx` 字样 0 处）。

### 验证
| 视口 | wrapper top | fab rect | computed bottom |
|---|---|---|---|
| 375×812 | 0 → **538** | 538~592 | 220.0px（= 50 + 340/37.5×18.75） |
| 390×844 | 8.3 → **561** | 561~617.2 | 226.8px |
| 1280×800 | 10.7 → **451.3** | 451.3~523.3 | 276.667px（= 50 + 226.67，340rpx 在 500px 封顶宽下 = 226.67px） |

悬浮球回到输入栏上方（375 档：球底 592，输入栏顶 654.1，间隙 62px），且与输入栏无重叠。

## 4. 验证方法（可复现）

关键点：**这三处缺陷在构建日志、类型检查、既有单测里都不会报错** —— 必须真浏览器量几何。

```bash
# ① 多视口几何量测（线上）：起 headless Chrome + CDP，注入云 SDK 桩并挡掉 CDN 真 SDK，
#    再点掉开屏封面，逐子元素转储宽度
bash .tmp-verify/inputui/run.sh

# ② 干预验证（改源码之前先证明根因）：在浏览器里注入候选修法，看坏值是否变好值
PROBE=.tmp-verify/inputui/probe-intervention.mjs bash .tmp-verify/inputui/run.sh

# ③ 本地构建产物复测：起静态服务 + Chrome，同一套断言
bash .tmp-verify/inputui/run-local.sh
```

脚本与产物都在 `.tmp-verify/inputui/`（临时验证目录，不进 `dist/`、不进版本控制）。
`measure-v2.json` / `intervention.json` 是原始读数，`bottom-*.png` / `top-*.png` 是截图。

**为什么先做"干预验证"再改代码**：直接改源码再测，无法区分"我修对了"和"问题本来就会自己好"。
先注入候选修法得到 `0px → 137px` / `17px → 0px` / `top 0 → 474` 三个明确变化，才把假设钉成根因。

   <Text className={styles.miniTag} style={{ marginTop: '8rpx', display: 'inline-block' }}>

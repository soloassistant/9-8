# 「私人晨报助理」微信小程序竞品对标

> 调研日期：2026-09-24　｜　撰写人：许清楚（产品经理）
> 口径说明：**本报告只针对微信小程序**，与同日那份《46 个上市软件竞品差距分析》是两套独立调研，结论不互相套用。
> 未修改任何代码文件。

## 0. 先看这里：我这次调研的三个硬约束（决定了报告怎么写）

**约束一：我无法真机打开小程序。**
所以我**没有**任何一条结论是"我打开看过"。每一条都按你要求的三级证据标注：

| 标记 | 含义 |
|---|---|
| `[实测]` | 本项目代码/配置里能直接读到的事实（我会写明读的是哪个文件） |
| `[有公开来源]` | 有可点击的公开页面/文章作为出处（官方文档、厂商官网、公开复盘文） |
| `[有公开来源-第三方]` | 出处是第三方博客/测评/问答，非官方，**可能与现状有偏差，需复核** |
| `[推断]` | 我基于已验证的平台规则做的推导，**不是事实现察** |
| `未验证` | 查不到。我不猜。 |

**约束二：微信的机制规则是"对所有小程序一视同仁"的，所以可比性最强的其实不是"某个小程序做了什么"，而是"平台允许什么"。**
因此本报告中「个人主体能做吗」这一列，我优先用**已验证的平台规则**来判定（个人主体能否开支付、能否用 web-view、能否选深度合成类目、订阅消息怎么发），而不是假装我知道某个竞品小程序的内部实现。这样即使某个竞品的细节我标了 `未验证`，「个人主体能做吗」这一列依然是可靠的。

**约束三：合规口径不改。** 全文坚持：公开源 + 强制标注来源 + 不转载正文只出摘要。

> **由 R10 + R7 推出的关键结论（本报告最重要的一条）**：
> 如果坚持**个人主体**，我们的**用户触达通道只剩小程序一次性订阅消息一条**（服务号开不了、订阅号无法认证因而模板消息也用不了、长期订阅拿不到）。这意味着：**一次性订阅的授权率，就是这款产品留存能力的上限。** 这句话后面会反复用到。

## 5. 我最该先做的 3 件事（可直接派工程师）

### 第 1 件：去 We分析 把数取回来（今天就能做，零代码）
**做什么**：登录 https://wedata.weixin.qq.com/ ，用小程序账号直接进入（创建小程序时已自动生成 We分析 账号）。**不做任何代码改动**，先连续记录 7 天，把这 6 个数抄进一张表：

| 指标 | 在哪看 |
|---|---|
| 打开次数 | 数据分析 → 访问分析 |
| 活跃留存 D1 / D7 | 数据分析 → 访问分析 → 留存 |
| 人均停留时长 | 数据分析 → 访问分析 |
| 分享次数 / 分享人数 | 数据分析 → 访问分析 |
| 添加到「我的小程序」人数 | 数据分析 → 访问分析 |
| 晨报页的入口页/退出页占比 | 数据分析 → 页面分析 |

**为什么是它**：我们现在连"用户会不会主动打开"这个数都没有。**在拿到这个数之前，任何留存优化都是在黑箱里调参。** 而且基础版免费、开通即用、无需部署——这是本报告里唯一一个"零成本就能消除盲区"的动作。
**验收**：7 天后产出一页基线表，标注这 6 个数 + 一句话判断（例如"打开次数 X，其中来自分享的比例 Y%"）。

### 第 2 件：重做一次性订阅的授权获取（这是个人主体唯一的触达通道）
**做什么**（可直接拆成 4 个子任务）：
1. **弹窗位置**：在"读完晨报"或"连续天数签到成功"页之后调用 `wx.requestSubscribeMessage`，**首屏和冷启动页绝对不弹**。
2. **模板与文案**：最多带 3 个模板；文案写成具体好处（"明天 7:30 提醒你读晨报"），不用"开启通知"。**参考死了么打卡的做法**：打卡成功页弹窗、文案说明"授权后，XX 才能收到 XX"。
3. **合规红线**：**订阅了才有提醒，不订阅照常能读晨报**——绝不强制（强制订阅属违规）。
4. **后端计数**：新增 `subscribe_count` 字段；**`subscribeMessage.send` 返回 errcode 43101（用户拒收或次数不足）时不要扣减次数**，单独标记；同时建立"已拒绝且记住"名单，避免重复弹窗。

**为什么是它**：由 R7 + R10 推出——个人主体拿不到长期订阅、开不了服务号、订阅号无法认证因而模板消息也用不了，**一次性订阅是唯一的触达通道**。所以**授权率就是这款产品留存能力的上限**，而且用户勾"拒绝并记住"后**不可逆**。这个动作越晚做，能触达的用户池越小。
**验收**：授权弹窗曝光率、同意率、43101 占比、次日成功下发率。

### 第 3 件：把 07:30 定时推送从"能跑"改成"不静默丢"
**做什么**：
1. `runScheduled()` 改为**分批 + 并发 + 游标续跑**，每批控制在云函数超时（20s，上限 60s）以内。
2. **参考死了么打卡的任务队列方案**：与其每次全表扫描，不如在用户设置/订阅时写"待命任务"记录，触发器只扫到点且未完成的任务，执行完标记完成。
3. **加执行日志与失败告警**：每批执行完写一条记录（成功数/失败数/耗时/最后处理的 openid 游标）；连续失败必须可见，**绝不能静默中断**。
4. 顺带修 P0-2 的连带问题：`limit(1000)` 是硬上限，超过 1000 用户直接漏发。

**为什么是它**：触发器已经存在（07:30），所以问题不是"有没有"，而是**"规模一起来就静默失效"**——前 N 个人收到、后面无声无息。这种失败最危险，因为它不报错、不告警，你会发现"怎么留存这么差"却查不到原因。而它和第 2 件是同一条链路：授权拿到了，推送却发不出去，等于白做。
**验收**：压测 ≥1000 用户时全部用户都能收到；人为注入超时后，系统有可见告警且能从断点续跑。

# 一、🔴 安全

## S-1【阻塞】`webSearch` 接受客户端自传身份，可冒用任意用户 ✅已复核

```js
// cloudfunctions/webSearch/index.js:1105（feedback）与 :1240（briefing）
const openid = ctx.OPENID || (event && event.openid) || '';
if (!openid) return { code: -1, message: 'no openid', data: null };
const user = await getUser(openid);      // :1243 读档案
const subscribed = isSubscribed(user);   // :1244 读订阅态
```

**为什么等于无防护**：小程序端 `ctx.OPENID` 由平台注入；**H5 根本没有微信上下文，`ctx.OPENID` 恒为空**，所以永远落到 `event.openid`——**调用方自己填的字符串**。`if (!openid)` 只在两者都空时拒绝，形同虚设。

**可利用性：高。** `webSearch` 正在 `src/services/dataSource.ts:34` 的 RPC 白名单里（正是为了让 H5 能调它），端点对**任何 H5 注册用户**开放：

| 攻击 | 后果 |
|---|---|
| `action=briefing` + `openid=<受害者>` | 读其 `nickname`/`preferences`/`subscribed`/`expiredAt`；`rankByPreferences` 还按其偏好排序 |
| 反复调 `briefing` | `checkIntelQuota`+`consumeIntelQuota` **烧掉受害者的 LLM 额度** |
| `action=feedback` | 以受害者身份写 `newsFeedback`，污染其画像 |

**讽刺**：`dataSource.ts:21-27` 注释里明写禁令——「客户端自传 openid 既被平台明令禁止，又可被冒用（谁都能填别人的 id）」。**禁令写了，实现没照做。**

**修法**：删掉 `|| (event && event.openid)`。定时/聚合路径确需跨函数传 openid，正确做法是服务端 `cloud.callFunction` + 签名单独通道，不能让「客户端能碰到的同一个入参」兼任身份凭据。
**改前必须先确认**：`getBriefing` 定时路径目前怎么传 openid，否则会修出新问题。

## S-2【阻塞】7 个云函数完全没有身份断言

`chat`/`extract`/`deleteAccount` 都有 `if (!OPENID) throw`，这七个没有，`undefined` 直接当身份：

```
getLibrary:6,9            where({openid: OPENID}) 读全量
updateSettings:6,25,31    无身份读写 users
confirmItem:9,24,40,58    无身份写 events/todos/items
shopping:23,28,35         无身份读写购物清单
createOrder:12,31         无身份写订单
login:6,10,20             无身份 users.add()
getUsage:64,68-70         无身份读 users/usage/items
```

**当前被 `RPC_ALLOWLIST` 挡着，但那是纯客户端闸门**（`dataSource.ts:58` 前端抛错），管不住服务端是否把它们挂成 RPC。而 `dataSource.ts:45-47` 自己写着「无法确认每个云函数是否注册为 RPC，**需要登录态下跑一次冒烟才能定论**」——**这个冒烟至今没跑过**。

**修法**：七处各补一行 `if (!OPENID) throw new Error('no openid')`，与 `chat`/`extract` 对齐。不依赖前端闸门。

## S-3【已核查安全，不必重查】

- `normalizeRef`（`intelGroups.ts:123-130`）只返回 `{text, source}`，**不透传 url**
- `src/` 全域 `dangerouslySetInnerHTML`/`eval`/`new Function`/`innerHTML`/`postMessage` —— **零命中**
- 购物清单 5 处写路径越权校验**正确**，无遗漏
- `createOrder` 价格来自服务端 `PLANS` 常量表，不可篡改；早鸟名额刷不满
- `webSearch` 的 `aiFilter` 分支不涉用户态
- **密钥扫描：零真实密钥**；`.env.local` 被 `.gitignore` 双重规则覆盖（但本机无 git，**未验证历史上是否已被 track**）

## S-4【理论风险】`externalLink.ts:19,21` 零 scheme 校验

`window.open(url)` / `window.location.href = url` 无协议白名单。**当前不可达**（url 全来自静态配置，用户输入只在编码位上），但这是公共 util，没有「调用方必须保证静态」的契约。将来任何一处改成接口下发即成存储型 XSS。

**一行修复**：`if (!/^https?:\/\//i.test(url)) return 'failed';`

### 🔻 复核结论：数据侧完全查无此症

`.tools/.probe-url-hosts.js` 对 `dist/api/hotspot.json` 全量 220 条做主机体检：


- **字面 URL**（数据里存的、用户点的东西）全部是各源**正规域名**，没有污染；

「用户点进去是否撞墙」仍是**未证实**的假设 —— 需要真机或无头浏览器逐条跟随才能定论，
在那之前不应据此做降权/移除源的产品决策（见问题总表 E2）。

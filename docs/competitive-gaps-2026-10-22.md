## 一、执行摘要

- 本版在 10-19 版（G1-G20）基础上重跑产品侧实证：**6 项已关闭或已落地**（推送时间偏好、三通道支付代码、
  记账导出、同步冲突裁决、分享 AI 标识、系统日历单向写入），**1 项降级为半成品**（跨源同事件合并
  只有前端 UI、云函数不产字段），**新增 1 个全新 P0**（G03 支付通道选型违反虚拟支付规则，
  前序版本未覆盖的平台规则），主体资质项（G04）由 10-13/10-19 版的 I-1/G4 合并升格为独立 P0；
  另新补齐记账/比价/习惯/学习/语音五条竞品线的本轮实测事实。
- 结论：共 **28 条不足**（P0 × 5、P1 × 16、P2 × 7）。与 10-13 版（27 条）相比，构成从「代码缺口为主」
  变为「**部署阻塞 + 平台规则 + 内容供应链**为主」——纯代码能补的差距大部分已补或已有方案，
  剩下的痛点是「最后一公里」与「结构性限制」。
- **Top 5 最痛差距**：① 云函数无法部署（服务端改进对线上用户全部为零）；② 订阅消息模板空串 +
  一次性订阅结构限制（「每日晨报」在主形态里没有可靠触达通道）；③ 订阅支付走错通道
  （虚拟商品须走小程序虚拟支付）；④ 主体资质双类目阻塞（资讯 + 深度合成个人主体均不可做）；
  ⑤ 情报无原文链接 + 跨源合并不落地（晨报内容核心体验）。

## 四、不足清单（28 条）

> 格式：不足描述 ｜ 参照的真实竞品/上市软件（含可查事实）｜ 差距等级 ｜ 代码证据。
> 等级口径：**P0 阻断级**（不做则无法上线/变现/触达，或有下架点名风险）；**P1 明显级**
> （用户直接可感地与竞品拉平体验）；**P2 打磨级**（差异化与增长放大器）。

### P0 —— 阻断级（5 条）

#### G01 云函数无法部署，服务端改进对线上用户全部为零
- **不足**：免费情报档、内容信任过滤、msgSecCheck、按时分流的定时推送、三通道支付回调——全部只存在于本地，
  线上跑的是旧版云函数。所有「竞品差距」在这一条面前都变成纸上优势。
- **参照**：任何已上市产品的线上服务（Morning Brew 每日送达 400 万+读者、墨迹天气早晚提醒到点到达）；
  这是本产品与一切上市软件的**基础设施级差距**。
- **证据**：`AGENTS.md` §5 / `MEMORY.md` 阻塞项——缺 `WX_APPID`/`WX_PRIVATE_KEY_PATH`/`WX_CLOUD_ENV`，
  `.env.local` 仅 266 字节（2026-10-22 实测），`project.config.json` appid 仍为 `touristappid`。
- **方向**：主理人侧提供 AppID + 云环境 ID + 支付密钥路径，部署后本清单中 G02/G06/G09/G11/G19/G20/G23
  的代码侧即自动兑现。

#### G02 订阅消息模板 ID 空串，「每日晨报」推送链路一次都不发
- **不足**：整条推送基建（五槽位 cron、按用户时分流、分批并发、预算控制）已就位，但
  `SUBSCRIBE_TEMPLATE_ID=''` 使前端授权 noop、云函数无模板可发——用户永远收不到第二天的晨报。
- **参照**：Morning Brew（固定时间邮件送达，400 万+读者）；墨迹天气「天气早晚提醒」自选推送时间
  （小米应用商店更新日志 2026-10-14）；滴答清单「微信提醒」双保险（官网 2026-10）——
  三者共同证明「到点到达」是晨间产品的留存地基。
- **证据**：`src/config/subscribe.ts:12` 空串；`src/pages/briefing/index.tsx:467/662/677` 调用点；
  云函数侧同名环境变量亦未配（`docs/云函数部署指南.md` 要求两处同值）。
- **方向**：公众平台选用/申请订阅模板 → 前端 `src/config/subscribe.ts:12` 与云函数环境变量两处同值填写。

#### G03 订阅支付走错通道：虚拟商品（订阅内容）须走「小程序虚拟支付」

- **参照**：Morning Brew/theSkimm 邮件触达无授权衰减（theSkimm 工作日 6:00 美东固定送达、

- **方向**：产品叙事改为「打开即见 + 到点提醒」双轨；评估企业微信客服消息/服务号作为补充通道；

- **方向**：当日有被挪项时晨报首屏显著披露（AI 为保护习惯挪了这几件事 + 原因 + 撤销）；
  补打卡与连续天数（复用 readStreak 的模式）。

### P2 —— 打磨级（8 条）

#### G22 信源窄且结构单一：无社媒/短视频/公众号深度流，中文垂直源大面积失效
- **不足**：情报面只有 RSS + 通义联网；48 个候选源 23 个失败，中文源仅 1 个通过，动物子类全军覆没，
  健康类只能靠科普杂志源——「按偏好排序」的原料库本身窄。
- **参照**：SmartNews 约 3000 家合作媒体 + 1000+ 频道（官网 2026-10）；今日头条多源 + 算法；
  微信「看一看/听一听」。
- **证据**：`docs/rss-尽调/rss-vetting-summary.md`（2026-10-21 实测报告）；
  `cloudfunctions/webSearch/index.js:47/88-92`（类目覆盖 + 中新网系源）。
- **方向**：短期按尽调报告的采纳清单补 18 科学 + 7 文化源；中期评估 DailyHotApi 类聚合板块
  （果壳/豆瓣影视已被其覆盖）；社媒/短视频源受资质限制不做承诺。

#### G23 晨报无固定栏目人设与「是什么/为何重要/接下来」三段式
- **不足**：每天一份报，但没有固定栏目结构和署名人格——读者对「谁在跟我说话」没有记忆点。
- **参照**：theSkimm「What's the story / Why does it matter / What's next」三段式（eathealthy365 2026）；
  Axios「1 big thing」+ Smart Brevity（官网 2026-10）；36氪 8点1氪 TOP3 + 热点导览（官方介绍文）；
  澎湃早餐湃五段式 + 主编/责编/图编署名（官网多期实例）；Morning Brew「约 5 分钟读完」的篇幅承诺
  （Hark News 2026）。
- **证据**：10-19 版 X2（仅语音有固定问候 `briefing:891-895`，无固定栏目人格）；G11（aiReason 未落地）。
- **方向**：头条 1 条（三段式展开）+ 快讯列表的固化结构；篇幅承诺（5 分钟/800 字内）；
  「AI 整理」署名已有，补一个固定栏目名即可形成人设。

#### G24 语音播报无音色选择、无打断、无连续对话
- **不足**：TTS 是分块队列播报（微信同声传译插件 1024 字节分块），不能打断、不能选音色、
  不能连续对话——「语音播报」是产品卖点之一，体验层停留在「朗读完就走」。
- **参照**：小爱同学：定制声音（20 句录音约 5 分钟复刻自己/亲人声音、可还原方言口音）+
  多音色（青葱/茉莉/蜜糖/泡芙童声）+ 全双工连续对话可随时打断（小爱开放平台文档 +
  小米 AI 实验室 MIDC 2020，本轮实测）；Gemini Daily Brief 语音播报当日要务
  （Google 官方博客 2026-08-26，前序核实）；Alexa+ AI 播客生成双主播节目（Amazon 官方，前序核实）。
- **证据**：`src/utils/tts.ts` 头部注释（分块队列、场景音色表仅 rate/pitch、插件无 rate/pitch 参数、
  无打断逻辑）。
- **方向**：P2 做音色选择（2-3 个预置音色，避开声音复刻的合规重量级）；打断播放是低成本高感知项，
  可从 P2 提前。

#### G25 单条资讯分享图缺失（带来源署名 + AI 标识）
- **不足**：转发分享已有品牌封面，但单条资讯的分享卡片没有——而分享图是最轻的裂变载体。
- **参照**：HabitKit「Turn any grid into a share card」打卡分享卡（官网，本轮实测）；
  多邻国分享连续天数/成就（duolingo.cn）；Morning Brew 推荐奖励裂变（Hark News 2026）。
- **证据**：10-19 版 X9/G14（`briefing:205` F30 品牌封面；单条分享图未见）。
- **方向**：单条分享图带来源署名 + AI 标识（合规红线内做增长）。

#### G26 待办与日程无时间块绑定、无番茄钟
- **不足**：待办与日程是两套列表，不能把待办拖进时间块；专注计时没有。
- **参照**：滴答清单：番茄专注 + 任务与日历视图联动 + 四象限/时间线多视图（官网 2026-10，本轮已核实）。
- **证据**：`grep 番茄|pomodoro` 全仓零命中（2026-10-22 实证）；10-13 版 B-4。
- **方向**：待办拖入日程时间块（复用现有日程编辑）；番茄钟为纯本地计时器，成本低。

#### G27 截图提取无多模态通道（云 SDK 纯文本限制）
- **不足**：收件箱三通道输入里的「截图」目前不能真正交给多模态模型识别——提取的是文本，
  截图内容要用户自己打字。
- **参照**：薄荷记账截图识别记账（华军软件园功能页，本轮实测）；小爱「超级小爱」圈搜/文档摘要/
  屏幕问答（xiaoai.mi.com，本轮实测）；豆包/通义图片输入（公开产品形态）。
- **证据**：10-19 版 G17（云 SDK `LlmMessage.content` 为纯文本，项目既有结论）。
- **方向**：评估供应商多模态接口或本地 OCR 预处理；属供应商能力问题，需先确认再排期。

#### G28 两个 H5 线上入口漂移 + H5 mock 回落可见性
- **不足**：gh-pages 与 workbuddy host 两个入口曾差一个合规提交，不同用户看到不同版本；
  且 H5 无微信上下文时云调用失败回落 mock——线上 H5 用户可能看到演示数据。
- **参照**：任何多渠道交付产品都以「单一事实来源 + 版本可查」为基本纪律
  （Morning Brew 邮件与 web 版同源，官网 2026-10）。
- **证据**：`AGENTS.md` §3.1（两入口漂移实例：曾差 `01f6296`，`panelNotice` 命中 0 vs 2）；
  `MEMORY.md`（H5 mock 回落 + DemoDataHint 要求）。
- **方向**：发布流程固定「两入口都查」的 30 秒核验（`curl | grep app.<hash>.js` 比对）；
  DemoDataHint 保证降级提示可见。

## 六、Top 5 最痛差距与产品方向建议

### Top 5 最痛差距

1. **G01 云函数无法部署**——免费情报、信任过滤、msgSecCheck、按时段推送、支付回调对真实用户全部为零；
   这是所有竞品差距的放大器，优先级高于一切功能差距。
2. **G02 + G06 每日晨报没有可靠触达通道**——模板 ID 空串（一条都发不出）叠加一次性订阅结构限制
   （长期订阅白名单不含本类目）。「每日」是这个产品的名字，触达却是最脆弱的一环。
   参照：Morning Brew 邮件 400 万读者、墨迹天气早晚提醒、滴答微信提醒，全部有到点到达的成熟通道。
3. **G03 订阅支付走错通道**——虚拟商品（订阅内容）按微信官方规则须走小程序虚拟支付；
   当前 pay-wechat 走普通云支付 unifiedOrder，存在合规风险；不变更通道，变现路径有硬伤。
4. **G04 主体资质双类目阻塞**——资讯类目个人主体不可做 + 深度合成个人不开放；
   个体工商户 + CloudBase 资质路径已被 2026-07 官方新闻验证可行，只差办理动作。
5. **G08 + G09 情报溯源与跨源合并不落地**——`intelItems` 无 url（不可点原文）+ `alsoFrom`
   云函数不生成（同事件重复播报）。这是晨报内容核心体验与竞品（今日头条/SmartNews/Feedly）的
   最直接体验差距，且两项都是纯代码可解、解冻即可施工。

### 产品方向建议（差距优先级框架）

- **第一梯队（上线前必须排爆，均为资质/配置/通道问题，不是功能问题）**：G01 部署 → G04 主体/类目 →
  G03 虚拟支付通道 → G02 订阅模板。这四件完成前，产品对真实用户不可用、不可变现、不可送达。
- **第二梯队（上线后 30 天，体验拉平）**：G08 情报原文链接、G09 跨源折叠、G10 已读/不感兴趣、
  G11 推荐理由、G19 免打扰生效、G20 试跑一次、G13 冲突重排、G12 天气深度。
  共同特征：**全部有代码基础或明确路径，随 G01 部署自动兑现一大半**。
- **第三梯队（差异化与增长）**：G23 栏目人设 + 三段式、G24 音色/打断、G25 分享图、
  G16 学习连胜机制、G15 结构化比价、G26 番茄钟、G27 多模态提取、G28 入口纪律。
- **明确不抄（差异化守卫）**：不抄 Motion 式全自动改日历（违背「先提议后执行」信任资产）；
  不立项系统日历双向同步（平台无读取 API，单向写入已够用）；
  不做社媒/短视频内容源承诺（资质硬阻塞，走 RSS/授权源路线）。
- **结构性限制的产品化对冲（G06/G07）**：微信小程序的触达天花板是真实的——把产品承诺从
  「每天推送给你」改为「**打开即见 + 到点提醒 + 邮件补位**」：晨报内容做成「任何时候打开都是今天份」，
  订阅消息做「到点喊你看」的单点提醒，H5 补邮件订阅。这同时是与 App 竞品（Kimi/元宝/豆包/
  墨迹）的形态差异化：调研确认四家定时简报均交付于 App/桌面端，**微信生态内的定时晨报尚无成熟对标**
  （10-21 文档第二节），空位真实存在，但要用工程纪律守住「设了不生效比没有设置更糟」的底线。

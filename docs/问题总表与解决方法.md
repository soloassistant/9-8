### A1 🔴 客户端自传 openid 身份冒用 — 已修

**问题**：`webSearch/index.js` 两处用 `ctx.OPENID || (event && event.openid)`。
H5 的 `database.rpc` 白名单放行了 `webSearch`，攻击者 POST `{action:'briefing', openid:'受害者'}`
即可让 `getUser()` 读出他人档案并消耗他人 LLM 额度。

**为什么不照报告原方案删掉**：`getBriefing:328` 每天 07:30 的定时任务**正是靠它代传身份**。
直接删会把定时晨报打废。

**解法**：`resolveCallerOpenid(ctx, event)` —— 有微信上下文时只认 `ctx.OPENID`；
无上下文时必须携带配对 `INTERNAL_CALL_TOKEN`（定长比较，防前缀短路）才接受 `event.openid`；
其余一律解析为空串，由各 action 既有的 `no openid` 分支拒绝。**令牌未配置时 fail-closed 并打 error 日志**，
不退化成裸兜底。

**验证**：`.tools/verify-prelaunch-fixes.js` A 组 11 条断言，含 4 类攻击用例（无令牌/空令牌/错令牌/令牌前缀）+ 1 条不误伤断言（正确令牌仍放行定时路径）。

### A4 🔴 外链零协议校验（存储型 XSS）— 已修

**问题**：`openExternalPage` 直接把 `url` 交给 `window.open` / `window.location.href`。
而 `url` 来自 **RSS 抓回来的外部内容**。一条被投毒的源给出 `javascript:...`，
弹窗被拦时的降级路径会在**当前页上下文**执行它。小程序分支复制出去同样是有害载荷。

**解法**：`isSafeExternalUrl()` 只放行 `http:` / `https:`，在**函数入口**拦（不是加个没接上的工具函数）。

**验证**：B 组 15 条断言，含 9 条恶意协议必须拒（`javascript:` / 大小写变体 / `data:` / `vbscript:` / `file:` / 协议相对 / 相对路径 / 空串 / 纯空白）、3 条正常必须放行、
1 条**行为级**断言：调 `openExternalPage('javascript:alert(1)')` 返回 `failed` 且 `window.open`/`location` 从未被触碰。

### A5 🔴 用户真实账号数字被当昵称公开渲染 — 已修（登录态实测发现）

**问题**：晨报页显示「**21094813**，中午好」，我的页显示「**21094813**免费版用户」。
根因 `localProfile.ts`：`maskIdentifier()` 只脱敏 email/phone，H5 会话只有数字 `user.id` 时返回空串，
于是落到 `id.slice(0, 8)` 兜底，把原始账号标识整串当昵称。

**为什么之前没发现**：`cloudAuth.ts` 的注释里其实记录过这个行为，但结论是「属行为变更需产品确认，故此处只标注不改」。
可把用户真实账号大字印在页头不是待确认的产品决策，是明确缺陷。

**解法**：数字 id 也脱敏（`id.slice(0,2)}***${id.slice(-2)}`）；兜底改中性称呼「晨友」（与小程序端 `login` 云函数默认值一致，用户可在「我的-称呼」自设）。

**验证**：产物内实测 `js/app.91f35e57.js` 中
`"nickname":L.nickname||maskIdentifier(x)||"晨友"`，且**全产物无 `nickname:...||...slice(0,8)` 残留**。

### B4 🔴 信任过滤根本没在管线上数据 — 已修（本轮最严重的一条）

**问题**：全仓 `assessNewsItem` / `filterNewsItems` 的命中位置只有一处实现 ——
`cloudfunctions/webSearch/index.js`。而**产出线上 H5 站点数据**的是另外两条链路：

```
.tools/fetch-data.js     → 写 dist/api/hotspot.json → 线上站点实际读的那份   ← 零过滤
.tools/static-server.js  → 本地 /api/hotspot 预览                          ← 零过滤
```

小程序端走 `webSearch` 云函数，**有**过滤；H5 / gh-pages 端**完全没有**。
也就是说一个过滤器只管了三分之一的出口：投毒条目能绕过它直接进线上站点、进用户视野。

**为什么之前没发现**：上一轮我拿 220 条真实语料跑过滤器得到「零误杀」，就当成它已经生效。
但那**只证明规则不误杀**，不证明它在管线上数据 —— 探针打的是规则本身，不是接线。
三份聚合逻辑各有一份拷贝，只有一份带过滤。

**解法**：把整段实现抽到 `cloudfunctions/webSearch/news-trust.js`（规则一字未改），
三处 `require` **同一个模块实例**：
- `cloudfunctions/webSearch/index.js` —— 小程序端
- `.tools/fetch-data.js` —— build 时产出 `dist/api/hotspot.json`
- `.tools/static-server.js` —— 本地预览

过滤点放在**跨源合并之后、剥离 `pubDate` 之前**：此时 entry 仍带 `pubDate`，
能被全字段判定；且早于写盘与缓存。丢弃数写进 `meta.dropped.untrusted` + `trustReasons` 便于观测。

**为什么放在 `cloudfunctions/` 内而不是 `.tools/`**：云函数部署只打包自身目录，
让云函数 `require('../../.tools/...')` 会在部署后直接崩。反向引用（`.tools` → `cloudfunctions`）
只发生在本地和 GitHub Actions 的完整仓库里，安全。

**验证**：新增 `.tools/verify-trust-wiring.js`（**25/25**），四组：
- A 组「三处 require 到同一个**模块实例**」（用引用相等判定，不是比对路径字符串）
- B 组「两个 tools 脚本真的在 merged 上调用了过滤器，且早于剥离 pubDate」
- C 组行为：4 条投毒样本只剩 1 条真新闻；3/3 全毒时 kept=0（护栏不得放回）
- D 组真实语料 220 条零误杀

原有 4 套 trust 测试（102 / 19 / 10 / 语料）全部保持绿，`__internals` 再导出使 require 路径不变。

### E2 🔻 「外链死链率约 8%」— 原结论已推翻，当前**未证实**

原报告写：「实测豆瓣电影 10/10 链接落到 `sec.douban.com` 登录墙；百度热点 5/10 落到验证码页」。

### ★ 附带发现：`vercel.json` 里的安全响应头在线上**一条都没生效**

`vercel.json` 声明了 `X-Frame-Options` / `X-Robots-Tag: noindex` / `X-Content-Type-Options: nosniff` /
`Permissions-Policy: geolocation=()` 等一批响应头。实测线上响应头是 **`Server: GitHub.com`** ——
**gh-pages 完全不读 `vercel.json`**，这些头**只在部署到 Vercel 时才起作用**。

⇒ 当前线上实际处于「**可被任意站点 iframe 嵌套** + **可被搜索引擎收录**」的状态。
⚠️ 同时提醒两件容易搞错的事：
1. 别拿 `Permissions-Policy: geolocation=()` 当成「H5 拿不到定位」的证据 —— 它在 gh-pages 上根本没被下发；
2. 上线前必须先定下**到底部署在哪**（Vercel 还是 gh-pages），否则这份 `vercel.json` 就是一份
   「看起来有安全策略、实际一条都不在跑」的假配置。

根因（已核实，别再靠猜）：**Pages 的源是 `gh-pages` 分支的根目录，不是 main。**
- `GET /repos/soloassistant/9-8/pages` → `source: {branch: "gh-pages", path: "/"}`、`build_type: legacy`；
- 实测 `gh-pages` HEAD 停在 `34f16b0`，**我这几次 push（`ca8cb04` … `1ec1ff2`）一个字节都没碰到它**；
- `.github/workflows/checks.yml` 只跑检查（typecheck/selfcheck/四条回归），**没有部署步骤**；
  `refresh-data.yml` 只往 `gh-pages` 提交 `api/hotspot.json`（那是 00:53 那次
  "pages build and deployment" 的来源，与 app 产物无关）。
- ⇒ **发布 = 把 `dist/` 推成 `gh-pages` 上的一次提交**，是独立的手动动作。
  ⚠️ 该动作的入口脚本 `.tools/deploy-gh-pages.cmd`（读 `dist` → `read-tree --empty` → `commit-tree`
  → 推 `gh-pages`）**没有入库**（被 `.gitignore` 的 `.tools/*.cmd` 规则挡住）——
  也就是说**这台机器之外没法复现发布流程**，建议后续单独处理。

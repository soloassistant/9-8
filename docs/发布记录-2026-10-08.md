## 三、本版包含的改动

### 1. 桌面端整页塌成 0 宽（P0，上一版修复，本版正式上线）

`≥500px` 视口下 `.taro-tabbar__panel` 宽度为 0：该元素是 column flex 的子项（`flex:1 1 0%`），
其唯一子节点 `.taro_router` 是 `position:absolute`（脱离文档流），`margin:0 auto` 吃光自由空间
→ fit-content 退化为 0，连累 `.taro_router` / `.taro_page`。
修法：`@media (min-width:500px)` 给面板明确 `width: 20rem !important`（+ `max-width:100%` 兜底）。

**注意口径**：这条修复解决的是**容器几何**。外部审计报的「1280×720 全白」不能由此解释
—— 实测撤掉修复复现 0 宽后，逐像素仅差 **8.5%**，并非白屏（绝对定位的内容会逃出 0 宽父容器照常绘制）。
会话中另有一处 `AuthGate` 打断 Taro 页面生命周期导致的整页白屏，已更早修复，那才是"全白"的成因。

### 2. 移除客户端自传 `openid`（安全性）

平台文档（`cloud-service` / `references/database/code-generation.md`）原文：
> `cloud.database.rpc()` … **Identity is automatic** … **Never pass a token, user id, or owner id by hand.**

- `src/services/dataSource.ts`：删除 `withIdentity()`，不再往 RPC 请求里注入 `openid`；`RPC_ALLOWLIST` 闸门保留。
- `cloudfunctions/chat`、`cloudfunctions/extract`：改回只认 `cloud.getWXContext().OPENID`，取不到即抛错。

### 3. H5「注销账号」死路（合规）

`apiDeleteAccount()` → `cloudfunctions/deleteAccount` 只认 `getWXContext().OPENID`，H5 必失败；
且它不在 RPC 白名单内，`clearStorageSync()` 那段永远走不到，用户只看到「注销失败」。
现 H5 走 **登出 + 清空本机数据**，weapp 保持原逻辑。

### 4. `cloudSync` 删除钩子占位符类型

原来无条件写 `[]`；现按 key 类型给（数组 `[]` / 对象 `{}` / 标量 `''`），18 个 `SYNC_KEYS` 全覆盖。
**这是潜伏缺陷的防御性修复，不是线上故障**：当前无调用点会单独 remove 标量 key
（唯一的 `clearStorageSync()` 走 Taro 的 `localStorage.clear()`，不经过该钩子）。

### 8.1 本轮修掉的真问题

1. **会话无 `user.id` 不得抛错**（上一位同学的 `buildProfileFromSession` 会抛）。
   SDK 的 `userFromSessionPayload` 是 `{ id: typeof r.sub === "string" ? r.sub : "", … }`
   —— **会话存在但 id 为空是合法状态**。据此抛错会让 H5 每次 init 都失败，比被修的 mock 更糟。
   改为只在**没有会话**时抛错；`openid` 留空（空是"不知道"，不是编造身份）。
2. `isHHMM()` 补**范围**校验（原来只验形状，`25:99` 能过），`23:59`/`00:00` 保留。
3. `apiUpdateSettings` 先确认会话再落盘（原来会让"保存失败但值已改"）。

### 8.2 关键：线上是 `2fedd178`、本地最新是 `de0f420b`，但两者**功能完全一致**

`1ca6412` 只改了注释，却让入口文件名变了。已查实原因：

- webpack 的 `[contenthash]` 取自**压缩前**的模块内容 —— 注释计算在内 → 哈希变 → 文件名变；
- 压缩（terser）随后把注释丢弃，于是最终产物里**只剩横幅中那个自引用文件名不同**。
- 全文扫描 1,864,212 字节：**只有 1 处差异块，offset 43..51，8 字节**
  （`app.2fedd178.js.LICENSE.txt` ↔ `app.de0f420b.js.LICENSE.txt`），其余逐字节相同。
- **构建是确定的**：无改动连续重建，仍得 `app.de0f420b.js`。
- 注释**没有**被抽取到 `.LICENSE.txt`（已核对该文件无匹配）。

结论：线上 `2fedd178` 已包含本轮全部功能改动；`de0f420b` 与之仅差横幅 8 字节。
**故没有为一条注释再发一次版**（再发＝零行为变化的线上覆盖）。
下次审计若比对到本地文件名与线上不同，请先做一次"除横幅外是否全等"的比对，别直接判"没上线"。

### 8.3 SDK 事实：`maskIdentifier` 的 email 分支在 H5 上**不可达**

查 `@tencent-ai/workbuddy-cloud-sdk`（`lib/index.global.js`）坐实，非推测：

| 函数 | 产出 | 被谁用 |
|---|---|---|
| `userFromSessionPayload(r)` | `{ id, name, avatarUrl, isAnonymous, raw }` —— **无 email / phone** | `parseSession` → 会话 |
| `parseUser(r)` | `{ id, email: r.email ?? r.user_metadata.email, phone, … }` | **仅** `auth.getUser()`（`/v1/user/me`） |

而 `getSession()` → `sessions.ensure()` → `store.read()`，读的是 `parseSession` 的产物。
⇒ **H5 的 `session.user.email` 恒为 undefined**，昵称会回落到 `id.slice(0, 8)`，
**不是**注释里承诺的"脱敏邮箱"。小程序端不受影响（那边 `login` 云函数本来就返回 email）。

**未改行为** —— 让它真生效需要改调 `getUser()`（多一次网络往返）或从 `user.raw` 取 email
（**未证实** `/v1/token` 响应是否带 email），两者都是产品决策。已把依据写进 `maskIdentifier` 的注释。
